# Agent Note: 时间选择器把转盘前置，常用时段按使用频率生成并换行展示

Status: implemented

## Problem

时间选择器有两处摩擦（issue #105）：一是 `datetime` 模式下日历排在时间区之前，时/分滚轮要下滑才能看到；二是「常用时段」是写死的上午偏多列表，并放在横向 ScrollView 里，屏幕上只看得到前几个（07:30–12:30），所以读起来像「只有上午」，更不会随用户实际使用变化。

## Decision

- `apps/mobile/components/datetime-picker.tsx` 按窗口宽度重排弹窗，而不是继续在固定宽度里挪顺序：
  - **宽窗口（`width >= 720`）**：`datetime` 弹窗用 `max-w-4xl`，顶部横幅下方是左右两栏 —— 左栏为快捷日期 + 日历网格，右栏为时间区（时/分滚轮 → 分钟工具条 → 常用时段）。日期与时间同时可见，大窗口里不需要滚动。`date` / `time` 模式用 `max-w-2xl`，内容居中限制在 `max-w-xl`，不把单列控件拉成通栏。
  - **窄窗口（手机）**：保持单列，顺序为 顶部状态横幅 → 时间区 → 快捷日期 → 日历网格。时间区因此紧贴横幅，滚轮出现在首屏；日期网格继续放在下方，需要时向下滚动。
  - 弹窗最大高度统一放宽到 `94vh`（compact）/ `92vh`（其余），宽度和高度都按窗口尺寸取，不再固定 `max-w-md`。
  - 跨 720px 时两套布局分支会重新挂载滚轮；同步滚动偏移的 effect 依赖 `isWide`，并用最新的 `hourRef` / `minuteRef` 重新 `scrollTo`。只依赖 `mode` 会让新滚轮停在 0，而顶部仍显示原时间，导致可见行与确认值不一致。
- 「常用时段」放在滚轮之后，并从横向 `ScrollView` 改为 `flex-row flex-wrap`。chip 区可以随使用记录增长并向下换行，但不会把滚轮或选中行顶出外层滚动区；所有 chip 直接可见，不再有横向滚动门槛。
- 新增 `apps/mobile/lib/time-presets.ts`：设备本地计数器，key 为 `nextdo.settings.time-presets`，JSON 形状 `{ "counts": { "HH:mm": n } }`；沿用既有的平台存储矩阵（native → `expo-secure-store`，web/Tauri → `localStorage`，Node/jest → 内存）。计数不裁剪：`HH:mm` 最多只有 1440 个合法键，本身有界；只把展示限制在前 4 个常用时刻，避免截断让新时刻永远累计不起来。
- `buildQuickTimePresets` 先放使用次数最高的 4 个时刻，再追加 8 个默认时段（07:30、09:00、12:30、14:00、18:30、19:30、21:30、22:30），去重且不裁剪默认值，因此上午/下午/晚间的覆盖不会因使用数据而消失。
- `apps/mobile/hooks/use-quick-time-presets.ts` 在弹窗挂载时刷新缓存；`confirm()` 记录一次使用：`time` 模式总是记录；`datetime` 模式只记录真正改动过的时刻，避免日期变更把旧时刻当成新选择。写盘是 fire-and-forget，失败只记日志，不阻塞关闭弹窗。
- 轮盘的 `onScroll` 在算出的时/分与当前值不同时置 `timeTouched`。此前只有点选按钮和预设会置位，`datetime` 模式下滑动滚轮后确认会静默退化成「只记日期」；挂载时的程序化滚动落在原值上，因此不会误标为选择。
- 程序化选择（chip、分钟快捷、±m 微调、上午/下午切换）调用 `scrollTo` 时一律 `animated: false`。平滑滚动会在动画期间回放旧偏移的 `onScroll`，把用户刚选的时刻写回旧值；Web 上动画可能延迟启动，点 preset 后立刻按「确定」会保存点击前的时刻。瞬时跳转先落到目标偏移，不再有回写窗口。

## Alternatives considered

- **从现有 action / reminder 行统计时刻** — 不新增存储，且天然跨设备。否掉原因：选择器需要在弹窗内同步拿到数据，引入 PowerSync watch 或跨表查询会把纯 UI 组件绑到数据层；而且用户选了但未保存的时刻不会计入。
- **写入 issue #97 的同步 settings 表** — 可以让使用习惯跨设备。否掉原因：这是单设备的界面便利项，把新 key 加进同步面会扩大账号数据契约，收益不足。
- **保留横向滚动，只调整 chip 顺序** — 改动最小。否掉原因：问题的一半就是「下午/晚上藏在屏幕外」，换成使用频率排序后仍然要横向滑动才会发现。
- **日期/时间做成两个 Tab** — 各自首屏都很短。否掉原因：为布局问题引入新的分段状态和切换成本，且用户经常需要同时看日期与时刻。
- **只把日历移到时间下方，仍保持固定 `max-w-md` 单列** — 不需要重排 JSX。否掉原因：桌面窗口很宽时弹窗仍只有 448px，日期与时间不能同时看到，只是把滚动方向从「找不到时间」换成「找不到日期」。
- **所有窗口统一用超大弹窗 / 固定大尺寸** — 桌面观感直接。否掉原因：手机会被撑出屏幕，`max-h` 之外还要处理横向溢出；响应式阈值只需要一个 `useWindowDimensions()`。

## Consequences

- **收益**：桌面/平板打开 `datetime` 弹窗即可同时看到日历和时/分滚轮，不再在宽窗口里挤一个手机尺寸的小弹窗；手机上时间区紧贴横幅，选中行始终位于首屏可见范围。常用时段覆盖全天并随使用重排；最近常选时刻在下次打开时排第一，且新时刻能持续累计。
- **代价与已知上限**：手机上日期网格仍在时间区下方，需要向下滚动才能看到（屏幕高度不足以同时容纳两者）；窗口高度很小时两种布局都可能需要轻微滚动。默认值永不裁剪意味着最多 12 个 chip，chip 区因此可能高于首屏并需要向下滚动；使用计数不跨设备同步；`lib/time-presets.ts` 复制了其他设备本地设置模块的存储样板。计数存储上限由 1440 个合法 `HH:mm` 键自然约束。

## Verification

- `apps/mobile/lib/time-presets.test.ts`：默认值覆盖上午/下午/晚间、使用频率排序去重、脏数据解析、持久化计数与越界值忽略；49 个旧时刻各计 2 次后，两个新时刻交替选择都能累计到 2，证明存储不再淘汰。
- `apps/mobile/__tests__/datetime-picker.test.tsx`：`datetime` 模式首屏同时渲染滚轮与全时段 chip；滚动小时轮盘后确认会带上时刻；同一时刻确认 3 次后再次打开，该时刻排在 chip 第一位且默认覆盖仍在。响应式用例：`Dimensions.set` 到 1280×900 时出现 `datetime-picker-two-column`，到 390×700 时没有两栏且滚轮仍在；弹窗打开时在 1280↔390 之间切换，布局立即重排。jest 环境的 ScrollView 没有可观察的命令式滚动，滚轮偏移恢复由浏览器读取 `scrollTop` 验证。
- 浏览器实测（`/tmp/nextdo-browser-check/layout-update-flow.mjs`，Chrome headless；本轮日志 `/tmp/nextdo-browser-check/2026-11-23-browser-round3.log`）：
  - 1280×900 的 `截止时间` 弹窗卡片宽 896px；日历日格在 (576, 437)，时轮在 x 649 / y 345，两栏同一行，滚轮、日格与「确定」全部在视口内，无需滚动。

  - 390×700 保持单列：时轮 34–179 / y 228–388 在视口内，「确定」在 607；日历日格落在 y 753（视口下方，预期滚动）。
